# 单人发送与双通知通道设计

## 目标

导入工资表时排除汇总行；管理员可对单名已匹配员工发送工资条；选择双通知模式时，工作通知和应用内 DING 都向该员工的同一钉钉 `userId` 投递，并分别可追踪。

## 范围

- 导入预览根据当前匹配字段过滤汇总行。匹配值等于或以 `合计`、`汇总`、`总计` 开头的行不参与目录匹配或最终创建；返回 `ignoredSummaryRows` 供界面展示。
- 新增按工资条项目发送的 API，仅允许能够管理该工资表的主管理员、子管理员或工资表管理员调用。
- 单人发送重用与整批发送相同的投递逻辑，且只处理目标员工项目。
- `work_notice` 模式仅发送工作通知；`work_notice_with_ding` 模式要求工作通知和应用内 DING 都成功。
- DING 使用机器人身份和企业 `userId`，由 `DINGTALK_DING_ROBOT_CODE` 配置。未配置、接口失败或返回无 DING ID 都是明确失败，不允许静默降级。
- 每个通道的投递状态、远端标识和错误代码分开存储，重试只补发失败通道，避免重复投递成功通道。

## 非范围

- 短信或电话 DING。
- 员工个人 token、待办 API 和基于个人 token 的确认提醒。
- 定时任务调度器的生产运行；它在后续独立改动中接入队列或 cron，但现有投递逻辑会供其复用。

## 数据与错误语义

工资条项目的投递记录按 `batchId + employeeUserId + channel` 唯一，其中 channel 为 `work_notice` 或 `ding`。成功记录保存任务 ID，失败记录保存稳定错误码。双通知模式中任一通道失败，单人和整批操作均返回 `partially_failed`；审计日志记录通道、员工 ID 和错误码，不记录薪资值或机器人凭据。

## 验收条件

1. 含“合计”的姓名行不出现在导入预览的待匹配、已匹配或最终工资条中，预览显示忽略数量。
2. 单人发送只调用该员工的 `userId`，不会投递其他项目。
3. 双通知模式对同一 `userId` 调用工作通知和 DING；两者成功才标记该员工投递成功。
4. DING 未配置或失败时，操作明确失败且可从投递记录与审计日志定位；成功的工作通知不会因重试而重复发送。
